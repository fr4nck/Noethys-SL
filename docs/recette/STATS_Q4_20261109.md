## Convention de preuve Q4

Pour chaque objet, se referer a la liste nominative du [tableau Q3](STATS_Q3_MATRICE_20261109.md). Inventaire AST : **33/33 PASS**. **Aucun objet ne devient PASS complet sur la seule base des tests transversaux.** Les colonnes a qualifier separement sont :

1. **SQL / metier** : requete reellement executee sur SQLite synthetique puis, lorsque la syntaxe et le contrat le demandent, MySQL 5.7 jetable ; resultat compare a une reference calculee independamment ; modes `presents`/`inscrits`, filtres et bornes de dates.
2. **Cache / isolation** : valeur modifiee apres changement de filtres, changement de connexion, reutilisation du meme objet ; garder NON TESTE si aucun test individuel. Noter N/A justifie si l'objet n'a pas de cache.
3. **Rendu / ressources** : texte, tableau ou graphique effectivement produit, liens image MemoryFS ouverts, absence de collisions et sortie normale du processus natif. Un mock ne suffit pas pour Windows natif.
4. **Impression** : selection de l'objet, HTML d'impression, apercu, sortie/annulation et reouverture, sur un Windows installe pour la validation finale.
5. **Runtime installe** : ouverture du dialogue, choix d'activites, navigation parmi les 11 pages, zoom, fermeture, etat HWND et absence de blocage. Enregistrer version, SHA, preuve, code de sortie et incidents.

**Statut initial Q4 : inventaire 33/33, SQL individuel 0/33 complet, rendu 0/33 complet, impression 0/33 complete, runtime installe 0/33 complet.** Ces nombres indiquent la preuve disponible, pas necessairement l'etat intrinsèque du code.

### Q4-QF — regle metier obligatoire avant GO

- Le code de validite `UTILS_Quotients_validite.py` recherche les chevauchements **par `IDtype_quotient`**, donc plusieurs types valides peuvent coexister.
- `UTILS_Stats_familles._QuotientsAlaDate()` determine une valeur numerique unique par famille, independamment du type ; des valeurs differentes simultanement valides vont vers `a_verifier`. Des valeurs egales de types differents sont aujourd'hui fusionnees numeriquement. **Ce mecanisme n'est pas une politique metier validee.**
- **Decision a prendre** : choix explicite de type si les activites ne partagent pas le meme referentiel ; interpretation d'un ensemble multi-activites/multi-baremes ; date de reference des inscrits et des presents ; cas de QF absent, nul ou invalide.
- En l'absence de decision, **interdit** de choisir arbitrairement un type, de faire une moyenne, d'utiliser une valeur issue d'une autre activite ou de reclasser `a_verifier` comme QF zero. Conserver le comportement prudent existant et le STOP-GATE metier.
- Tests d'acceptation a concevoir sur types actifs egaux/differents, bornes inclusives, changement de periode, references successives, deux comptes payeurs, familles sans QF et plusieurs activites de baremes distincts.
